### 2. DDF具体拦截了什么

C实际尝试4155次、批准2659次、拒绝1496次，批准率约64.00%。B在自身轨迹尝试9551次，全部由CG批准；没有暗中根据Deadline拒绝。两者次数不是独立可交换样本，而是不同轨迹的请求事件数。

拒绝原因的互斥主分类：

| 原因 | 检查次数 |
|---|---:|
| 只损伤候选自身原按时性 | 1304 |
| 只损伤其他已知任务原按时性 | 85 |
| 同时损伤自身与其他任务 | 42 |
| 没有按时集合损失，但原迟到总超期增加 | 65 |
| CG单独拒绝 | 0 |
| 合计 | 1496 |

按可重叠标志统计，1431次涉及按时身份损失、98次涉及总超期增加，其中33次重叠；127次涉及其他任务。**87.17%的拒绝仅涉及自身按时性**，不能把所有价值都包装成群体日历独有贡献。不过85次“自身不受损而其他任务受损”明确展示了个人Slack检查覆盖不了的局部作用，65次纯总超期拒绝也体现了既定服务质量约束。

批准不等于实际主动等待：C批准2659次但实际主动等待2654个任务槽，其余5次按V2“容量先于defer”成为容量等待；B对应9551和9546。按真实账本分类，没有把这5次混入主动等待。不同任务身份可能被多次尝试，不能将尝试数当作任务数。

### 3. 局部保护为什么不等于全局EDF非恶化

C挽回了B新增762个违约中的705个，但C仍有98个A原按时任务最终违约，同时让151个A原违约任务按时；所以最终净减少53个违约。不能宣称C逐任务或全程DMR都不差于A。

对已保存C轨迹另外进行**纯事后日历重放**，不执行环境step、不增加性能回合、不读取新源数据：2592次决策的启动、两类等待、资源使用、参考按时数、超期量均重现一致；2583个相邻边界去掉新到达后，全部与上一批准计划后缀一致。1731个没有到达的边界直接一致。

全部277次按时预测丢失事件发生在40个有新任务到达的边界。C相较A新增98个违约的分类：

- 32个曾有批准计划中的按时预测，后来在已知集合增加时丢失；删除该边界新到达即可恢复原预测，证明该边界损伤不来自日历实现失配。
- 66个在其首次进入参考计划时就已预计迟到，此后从未获得按时批准预测；不能倒称DDF早已保证它们按时。

两个必要案例（完整身份见转移复核JSON）：March-OH某任务在1260分钟边界遇到90个新到达，预测Finish从1320.8变成1350.8，Deadline1336.2；April-OH某任务在315分钟遇到247个新到达，预测Finish从466变成511，Deadline496.5。删除边界新到达分别恢复原Finish。它们说明未知未来会改变EDF参考，而非证明某一个更早推迟单独造成最终miss。

**结论：DDF能正确识别并阻止已知集合中的部分危险推迟，真实规则轨迹的整体服务质量明显优于无DDF规则；它不提供未知未来的Deadline保证。**

## 第四部分：下一步明确决策

**CONDITIONAL GO；不建议立即启动正式E2训练。** 这不是平台工程失败，也不要求重建数据中心或放宽DDF。

最小后续准备：

1. **先冻结E2合法Train谱系分组。** 当前3个验收复用片段足够做本轮开发验证，不能支撑PPO额外价值或泛化的可靠模型选择。优先核验现有16个Train基础窗口是否可沿用相同Observed×1、时间轴与数据身份，按原始任务内容/连续时间块划分训练和Train内部留出组；不读取封存角色，不把容量/seed/复制窗口当新样本。若仍只有3个独立单元，明确降级为技术原型。
2. **冻结已有设计中的公平基线和训练契约。** E1按用户要求仅比较A/B/C，没有运行个人Slack保护臂。考虑87.17%为自身按时性拒绝，E2应保留既定个人Slack对照及“规则+DDF vs PPO+DDF”来判断完整日历和学习器各自贡献，而非用无Slack的B单独证明PPO必要。预注册训练预算、规则模型选择预算、奖励尺度、miss权重、评估与失败停止处理；不擅自加新保护或奖励项。
3. **保留完整责任门禁。** 本轮三条规则轨迹均CG通过，不保证所有未来探索策略都不会失败。发现CG失败、未完成或截尾时保留轨迹并暂停正式训练，不能删除低完成轨迹、扩大评价窗口或利用漏算电量获取低碳奖励。保持γ=1等V0.2既定契约。

这些准备不需要修改CPU/GPU/MEM、Deadline、Duration、CI、HVAC或动作空间。OH继续作为高压力场景，不能为了达到DMR≤5%删任务或降低统计。
