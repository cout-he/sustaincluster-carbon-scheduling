# A1：逻辑容量、条件性设备清单与 A2 资料缺口

本附录支持 A1 的资源调度验证和下一步设备设计，**不构成已校准机房清单，不授权 A2 修改，也不冻结最终研究对象**。A1 不调用旧 IT/HVAC 模型为候选容量计算真实电能、碳排放或制冷收益。

依据：A0 提交 `a754c5ee4bd3922cecd6993d9abb6bfbacdda7e0` 的[诊断报告](A0-research-object-diagnosis.md)、[统计附表](A0-statistical-evidence.md)，以及同一基线的 `utils/dc_config_reader.py`、`envs/sustaindc/datacenter_model.py`、`utils/make_envs.py`、`experiments/joint/power.py`。A1 新字段证据见[字段附录](A1-field-evidence.md)，候选配置在 `experiments/object_model_a1/configs/`。本附录没有读取任务或环境 payload。

## 1. 先区分四种容量

1. **观测用量**：trace 记录的 CPU/GPU/内存使用指标。即使单位核验成功，平均用量也不自动等于作业申请量、峰值需求或设备占用数。
2. **逻辑可调度容量**：调度器账本允许同时运行的资源上限。A1 可在明确版本和单位下用它研究容量竞争，但这并不自动产生实际服务器。
3. **物理安装容量**：逐台服务器、逐块 GPU、逐条 DRAM 的型号与数量。它必须有设备资料依据，与逻辑可分配量通过明确的保留/共享规则连接。
4. **电气与制冷容量**：IT 电功率、配电边界和制冷热移除能力。W electric 与 W thermal 是不同物理量，不能因都写作 W 而复用同一参数。

Alibaba 官方字段说明已支持 `cpu_usage/100` 为平均已用 vCPU 等价量、`gpu_wrk_util/100` 为平均已用 GPU 等价量、`avg_mem` 为平均已用 GB。因此 A0 的“原字段单位尚未确认”缺口已得到推进，**不能继续把 GB 单位本身写作未知**。但是，本地 sensor→实例→任务的连接多重性、聚合均值与平均 Duration 的块执行近似仍未通过原始表逐行实证，usage 也不是 plan。字段单位确认不等于实际申请量和设备清单确认。

逻辑 GPU 单位必须称 GPU-equivalent 使用容量，不能把数值 1,000 写成已经验证的 1,000 块实体 GPU。不能把分数使用量向上取整成申请 GPU 数，也不能给它补写 MIG、MPS 或虚拟 GPU 部署事实。vCPU 与物理核心/SMT 的关系也尚未确定。

## 2. L/M/H 的条件性整机算术

下表只回答：“**若另取得依据**将逻辑 CPU 单位对应到服务器可分配 vCPU、GPU 等价容量对应到可服务设备，并且将旧 reader 的 64 核/服务器解释为 64 个可用 vCPU 单位、至多 4 GPU/服务器、至多 25 服务器/机架作为条件设计假设，怎样避免设备数量算错？”64/4/25 来自现有软件设计常数，**不是 Alibaba 原机房清单，也不是本项目选定硬件的独立规格证明**。下表安装 vCPU 数不能在缺少 SMT/型号资料时改称物理核心数。

设 CPU 可分配容量为 C、GPU 设备容量为 G，暂不计系统预留，则服务器数算术下界为 `max(ceil(C/64), ceil(G/4))`。一种可行的计数草案是在 `ceil(G/4)` 台服务器安装 GPU，其余为 CPU-only；最后一架允许不满，不通过复制平均机架配置补齐设备。

| 候选 | CPU / GPU / MEM 逻辑容量 | CPU 所需服务器下界 | GPU 服务器数（每台 4 GPU） | 服务器总数下界 | 其中 CPU-only | 条件性安装 vCPU 数 | 条件性 GPU 对象数 | 机架数下界 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| L | 57,792 / 1,544 / 80,000 | 903 | 386 | 903 | 517 | 57,792 | 1,544 | 37 |
| M | 50,000 / 1,000 / 80,000 | 782 | 250 | 782 | 532 | 50,048 | 1,000 | 32 |
| H | 29,440 / 660 / 80,000 | 460 | 165 | 460 | 295 | 29,440 | 660 | 19 |

表中三种 GPU 数均可被 4 整除，不需要部分安装的 GPU 服务器。L/M/H 最后一架分别有 22/18/15 个未使用服务器位置；它们是空位，不能实例化为空闲耗电服务器。M 的 48 个额外安装 vCPU 来自取整，尚不是经过设计的系统预留。L/H 的算术下界恰好用尽 vCPU，不能据此宣称操作系统、守护进程、驱动或通信栈无需资源。Legacy ×5 是合成放大使用量；此表不把这种放大变成真实 GPU 申请。

### 2.1 Observed ×1 的重新推导与设备计数草案

Observed ×1 取消缺少独立物理依据的基本倍率 5，但保留显式压力因子 0.75/1/1.25。OL 根据未放大立即并发 CPU/GPU 峰值 11,552.278905/308.257695 重新按 64/4 向上取整；OH 根据 P95 5,876.042133/131.534380 重新取整；OM 将 M 的三维容量与任务需求同时除以 5，作为**归一化压力精确对照**。OL/OH 的取整属于可见设计变更，不是简单宣称与 L/H 完全同一容量。

| 候选 | CPU / GPU / MEM 逻辑容量 | CPU 所需服务器下界 | GPU 服务器数（每台 4 GPU） | 服务器总数下界 | 其中 CPU-only | 条件性安装 vCPU 数 | 条件性 GPU 对象数 | 机架数下界 | 最后一架空位 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| OL | 11,584 / 312 / 16,000 | 181 | 78 | 181 | 103 | 11,584 | 312 | 8 | 19 |
| OM | 10,000 / 200 / 16,000 | 157 | 50 | 157 | 107 | 10,048 | 200 | 7 | 18 |
| OH | 5,888 / 132 / 16,000 | 92 | 33 | 92 | 59 | 5,888 | 132 | 4 | 8 |

这三种布局同样仅为混合服务器的计数存在性草案。若所有服务器均装 4 GPU，安装数将为 724/628/368，而非 312/200/132。OM 的 48 个额外 vCPU 也只是取整余量。没有资料支持将它固定视为系统预留，更不能在 OL/OH 把预留默认为 0。80,000→16,000 GB 的容量变化是三维统一缩放对照，不是选定 16 TB 实际 DRAM 的规格依据。

这些是**两类服务器混合部署的存在性草案**。如果最终选择所有服务器均为 4-GPU 型号，则装机 GPU 数会变成 3,612/3,128/1,840，与上表的逻辑 GPU 数不同；多出的 GPU 必须逐个列明并解释为不装机、离线、保留或可分配，而不能在功率模型中消失。也可以采用专用 CPU 与 GPU 服务器，但那会改变 CPU/GPU 共置、系统预留、内存和功率设计，应在取得规格后另行定案。

### 2.2 系统资源预留不能由取整误差代替

正式设备设计应分别记录 `installed_cpu_cores`、`schedulable_cpu_cores`、`reserved_cpu_cores`、`installed_memory_bytes`、`schedulable_memory_bytes`、`reserved_memory_bytes`，满足安装量≥可调度量+保留量。若保留 CPU 核数为 R，计数应至少满足：

`N_server >= max(ceil((C + R)/64), ceil(G/4))`。

目前 R、每台 DRAM 容量、内存预留、GPU 驱动/运行时的主存开销均缺部署依据，均应保留 `null`，不先填写固定百分比。保留比例必须来自选定软硬件部署规范、可复现实测或有适用条件的来源。取得依据后需要重新校验容量是否仍对应 A1 竞争分层，而不能悄悄压缩可分配量。

`MEM=80,000` 是 Legacy ×5 的合成 GB 使用容量，Observed ×1 对照为 16,000 GB。原字段 GB 单位已确认，但逻辑可用容量不是 DRAM 安装规格，官方字段说明也未解决 GB 底数、均值到预留/峰值、系统内存开销和 DIMM 颗粒问题。因此 `installed_memory_bytes=null`、`memory_dimm_count=null` 仍然合理。不能将容量直接平分给服务器，再把商数声称为 DRAM 规格。显存与主存必须单列，不能因为原 trace 另有 GPU memory 使用字段就认为现有 MEM 账本已约束显存。

### 2.3 当映射改变时，L/M/H 数值如何处理

A0 的 57,792/1,544 与 29,440/660 分别来自 **Legacy 基础倍率 5、压力 1** 的立即并发需求峰值和 P95，按旧 64/4 粒度向上取整；M 是旧配置对照。它们不是脱离映射后仍成立的硬件真值。

A1 已提供有官方使用单位支持的 Observed ×1，并重新推导 OL/OH、用 OM 保留压力精确对照。它仍然是已聚合均值的流体资源模型，不能称 reservation/placement 模型。L/M/H 继续作 Legacy 逻辑竞争对照，以上整机表不随之获得物理真实性。倍率 5 不能充当真实 GPU 数或作业申请量的独立依据。

## 3. 改 GPU 容量需要同步改变什么

| 层次 | 必须显式处理的关系 | A1 边界 |
| --- | --- | --- |
| 任务需求 | 使用率、申请量、设备数、显存需求和可共享规则分开；不能通过缩小容量分母伪造每任务 GPU 数 | 在独立映射版本中记录来源和语义；未证实项明确缺失 |
| 设备清单 | 每块 GPU 有唯一设备 ID、型号、父服务器 ID、可分配状态；GPU 数应等于清单计数 | 上表只有条件性数量，不生成或运行旧 GPU 功率对象 |
| CPU 共置 | GPU 服务器的 CPU 核数、GPU 作业所需 host CPU、OS/驱动预留需要一致 | 不凭 GPU 数猜 CPU 开销，不改真实任务需求以配合硬件 |
| 主存与显存 | 每服务器 DRAM、每 GPU 显存和相应调度约束分别定义 | 已观测主存单位是 GB；安装/峰值/预留容量未核验者不填写，两种存储不混合 |
| 机架与配电 | 明确每架实际服务器位置、设备功率、网络设备和配电边界；末架允许不满 | 25 台/架仅为继承布局假设，不能证明功率密度适配 |
| 功率对象 | CPU/服务器底座/GPU/DRAM/风机分别计数；离线设备是否耗电由状态定义 | 禁止让一个 CPU server 对象隐式只带一块 GPU，随后却用四块 GPU 的逻辑容量 |
| 制冷 sizing | 根据完整 IT 设计热负荷、环境设计点、冗余和设备性能确定冷量与电功率 | 不是把 GPU 容量乘一个旧 W/GPU 系数即可完成 |
| 核算 | 负载需求、安装清单、可分配容量、利用率、功率、kWh 与 CI 积分使用同一版本身份 | A1 只输出资源调度与明确命名的 CI 代理，不产生物理碳结论 |

减少逻辑容量但保持设备不变，可以是准入控制或保留容量敏感性；增加逻辑容量但不增加设备，需要有可验证超售/共享机制。这两类都必须明确命名，不能描述成已经扩建/缩建机房。A1 默认不以它们为物理部署结论。

## 5. A2 的修改与验证顺序（尚未执行）

1. **先冻结输入语义和资产边界**：确认哪些 trace 字段是使用量、哪些是真实申请；确定资源单位、服务器/GPU/DRAM 清单、系统预留和功率测量边界。没有资料时保留缺失，不生成“完整”假规格。
2. **在独立 A2 实现中修正计数与端点**：逐服务器枚举 CPU 和其 GPU 列表；把 CPU/GPU/主存/风机与底座分开，进行设备计数守恒和 idle/full 端点测试。不得覆盖旧 V2/V3 模型及 checkpoint。
3. **分开热与电参数并建立闭合账本**：CPU/GPU/DRAM 等电功率形成 IT 热负荷；机房/冷却回路满足带明确储热项与损耗边界的热平衡；冷却移热与风机/压缩机/泵电功率分开。拆分 CT 热容量与风机电功率，统一 COP 配置入口。
4. **修复天气因果与温度状态**：使用有正确时区的已观测天气，或者明确标记环境真值和控制器可见信息；用真实湿空气变量计算所需湿球。入口温度需要随负荷/送风/回流变化，若要研究热安全与制冷协同，还需要有依据的热容/惯性或明确限制稳态适用范围。
5. **预先规定独立验证工况**：零/中/满负荷、多个室外工况、18–22°C 控制域，检查分项端点、设备计数、能量平衡、负荷响应与约束是否可能绑定。升温后 IT 与 HVAC 交叉若仍出现，必须能由校准分项解释，不能以“能产生更大协同收益”决定参数。
6. **再进行完整窗口核算**：统一 kWh 与 CI 的 UTC 时间积分，分别报告完整总量、相同设备/温度责任窗口的空闲基准和增量。若大量背景来源于资产规模或长尾窗口，应如实分解，不能只展示增量百分比替代总碳结果。

所有接受阈值应由数据精度、设备规格容差或预先规定的校准协议给出；本附录不填一个没有资料支持的误差百分比。A2 开始前仍需用户确认研究对象和修改方案。

## 6. 独立边界审核清单

主报告和候选配置在发布前应满足以下条件：

- Legacy 与新需求映射的标识、单位、倍率及来源单独版本化；不能把旧资源倍率 5 重命名为实体 GPU 数。
- 逻辑 L/M/H 仅在相应映射版本下有意义；新映射采用新的容量推导时，不沿用旧容量标签掩盖单位改变。
- 候选的可运行状态指资源账本可以运行，不意味着存在已验证服务器、可部署的分数 GPU 隔离或可信电碳目标。
- `equipment_inventory_status` 明确为未校准/未冻结；无来源的系统预留、型号、安装内存、电功率与制冷参数为 `null`，同时保留已经确认的 GB 字段单位。
- 所有任务保持不删减；容量不足、主动推迟、不可装入与未完成分别统计；DMR 分母和完整排空责任清楚。
- 公布各场景 DMR 和持续竞争时间，不只用 pooled DMR≤5% 给候选背书。
- 规则实验只读取 Train，A1 不运行旧 IT/HVAC，不输出看似真实的 kWh/kgCO₂；CI 代理和未来 CI 理想化分析明确标记。
- 修改 GPU 容量后没有只改利用率分母而悄悄复用旧 800 GPU 功率对象。
- 没有冻结最终研究对象，没有训练模型，没有进入 A2。
