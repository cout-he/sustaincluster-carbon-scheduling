## 1. 为什么同一个原始 Task 会有两条当前记录？

本轮重新扫描本地原始任务包，仅保留十组目标键的匹配记录，并与指定 Train 冻结文件及 A1.2 明细交叉核对：

| 核验项 | R01–R10 结果 |
|---|---|
| 每组原始 `(job_name, 原始start_time, 原始end_time)` 匹配数 | 均为 1，对应唯一 `task_name` |
| 每组当前行数 | 均为 2，合计 20 行 |
| 来源位置 | 每组同一 `source_row`，不同且相邻的 `source_task_index` |
| 到达时间、Duration、CPU/GPU/MEM 需求、SLA、数据中心 | 每组均相同 |
| 十二个原始字段中的差异 | 每组仅 `bandwidth_gb` 不同 |
| 当前稳定任务 ID | 20 个不同 ID |
| 原始 `inst_num` | 1：5 组；2：2 组；3：1 组；6：2 组 |

因此，重复已经存在于同一来源桶的任务矩阵位置中，不是执行器把一个 ID 重新入队，也不是年度平移到两个不同时间造成的。本轮十组的两行不能统一解释为两个真实实例：五组原任务只有一个实例，且预处理本来按 Task 聚合实例用量。

最有依据的生成机制是**计算任务表与带宽表的连接键不完整**。本地 `D:/A-myprofile/SustainCluster/upstream/data/workload/alibaba_2020_dataset/alibaba_analysis.ipynb` 的源码链为：

1. cell 12 按 `(job_name,task_name)` 汇总实例使用量；cell 19 导出 `extracted_dfas.csv` 时丢弃 `task_name`（文本第 1723 行），留下计算记录和原始起止时间。
2. cell 54 重新加载该 CSV。cell 55 将传感器带宽按 `(job_name,task_name)` 聚合（第 5468 行），所以同一 Job 在右表可能有多个不同角色的带宽记录。
3. cell 56 却执行 `dfas.merge(df_bandwidth, on=['job_name'], how='left')`（第 5521 行），随后删除来自右表的 `task_name`；cell 57 保存带宽版 CSV。
4. [年度生成脚本](../../../data/workload/alibaba_2020_dataset/extract_dataset_from_dfas.py) 第 346–372 行将每个桶的所有行转成矩阵，第 453 行再整体复制矩阵到年度时间轴；没有按原始 Task 身份消除连接扩行。

该连接中，一个计算记录会与该 Job 的每条右表记录分别配对。若右表有两条不同带宽值，就生成“两行计算字段相同、带宽不同”的结果；这与十组实测形态一致。一个 Job 可以有多个真实 Task，按 Job 连接不能保留角色归属。

## 2. 能否证明重复来自预处理连接？

**代码层面的扩行机制已证实；十组的完整历史来源链尚未证实。** 假定左表某 Job 有 `L` 行、右表有 `B>0` 行，当前连接产生 `L×B` 行，没有一对一/多对一校验。此机制可以直接解释现象，但不能拿观察到的两个带宽值反构造右表，再称之为原始输入证据。

本地按文件名复查 `D:/A-myprofile/SustainCluster`，仍未找到 `extracted_dfas.csv`、`extracted_dfas_with_bandwidth.csv`、`dfas.csv`、`dfws.csv`、`df_bandwidth*` 或原始传感器表。没有重跑 Notebook，也未下载其他表。十组所在 Job 在原任务表中分别有 1 行（5 组）、2 行（1 组）、3 行（4 组）；**原任务表行数不能替代实际传感器聚合右表的行数**，也不能据此断言每组右表恰有两条记录。

因此尚不能排除更早连接或中间数据版本差异的参与，不能证明两条带宽分别来自哪个真实角色。要完成逐条历史证明，需要对应十组的连接前计算记录及带宽聚合记录，并核对连接输出的字段、基数和内容哈希。

## 3. 当前模拟是否重复计入任务数量和资源？

**是，按当前代码完整消费这个片段时，两条记录分别进入计算任务账本，没有按原始身份合并。此判断来自输入核验与源码，不是本轮运行仿真得到的结果。**

- [V2 场景构建](../../../experiments/joint_v2/scenarios.py) 第 274–285 行逐矩阵位置创建 `TaskSpec`；[冻结加载器](../../../experiments/e1/workload.py) 第 110–114 行保留全部记录，第 48–59 行将稳定 ID 设为运行任务名。ID 含来源位置，因此每组的两条记录不会发生主键冲突。
- [执行器](../../../experiments/e1/engine.py) 第 153–169 行逐条建账、入队；第 28–34 行按每个运行任务的资源求和；[资源分配](../../../envs/sustaindc/sustaindc_env.py) 第 216–227 行逐条扣减资源并加入运行列表。[统计](../../../experiments/e1/metrics.py) 第 29 行按任务记录数计到达量。
- [A1 映射适配器](../../../experiments/object_model_a1/config.py) 第 70–74 行只缩放每行资源，保留原任务条数。因此 Observed ×1 也保留重复；改变容量或使用率分母不会消除它。

仅对这十组，当前为 **20 条记录而非 10 个原始 Task，计算需求各计两份**。以已核验的压力 1、Legacy ×5 冻结字段作静态求和：

|---|---:|---:|---:|
| CPU 逻辑需求 | 24.918621 | 49.837242 | 24.918621 |
| GPU 逻辑需求 | 0.055740 | 0.111480 | 0.055740 |

以上只是现有映射下的**声明需求总和，不是同时运行峰值、真实申请量或已执行资源用量**；比较基准不是已实施的去重数据集。两份资源何时实际分配仍取决于排队和运行状态。不能据此宣称利用率、DMR、能耗或碳排翻倍，也不能将十组结果外推到全部 Train。

## 4. 怎样修复才不会误删真实任务？（仅建议，待确认）

优先修复生成链，再产生独立新版本，保留旧数据及谱系：

1. 计算侧保留原始 `job_name/task_name/start_time/end_time`、来源版本及预定的 Task/Instance 聚合口径；额外保留年度或场景的**重放出现身份**。不同角色、真实不同执行、不同重放时间不能因同 Job 或同原始键而被全局删除。
2. 带宽按相同 Task 身份聚合后，用 `(job_name,task_name)` 接回计算记录，右侧要求每键唯一，连接使用 `validate='many_to_one'` 并断言输出行数等于连接前计算行数。左侧完整业务身份也需单独核验唯一性；此校验不能修复左表已有重复。缺匹配和冲突显式列出，不静默填造。
3. 对本轮十组，可建立“两个当前位置 → 一个原始 Task”的显式审计映射；在确认一个 Task 聚合为一个计算对象的口径后，重建一份计算记录。**不能直接 `drop_duplicates(job_name)`、保留第一条、按相同需求删行，或将不同带宽求和/平均作为修复。** 正确带宽应从该 Task 的可追溯来源重新取得；来源仍缺失时标记未解决，不能任意选择两个值之一。
4. 把 `inst_num>1` 的实例聚合与重复行处理分开，先说明一个计算对象代表什么，再核验任务数、需求总量和映射完整性。未来加入申请字段时，不能把同一 `plan_*×inst_num` 总量重复赋给两条独立计算记录。

本轮未实施上述方案，未修改数据、容量、Deadline、加载器或仿真器，未运行调度实验或训练。
