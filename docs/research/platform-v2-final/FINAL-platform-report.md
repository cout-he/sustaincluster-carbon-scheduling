## 4. CPU/GPU/MEM如何进入IT功率？

设聚合占用为`u_CPU,u_GPU,m_GB`，安装核`N_core`、CPU插槽`N_CPU`、GPU`N_GPU`、DIMM`N_DIMM`。瓦转kW：

```text
P_CPU = N_CPU × [45 + (205−45) × u_CPU/N_core] /1000
P_GPU = N_GPU × [25 + (250−25) × u_GPU/N_GPU] /1000
P_MEM = N_DIMM × 3 /1000
P_host_other = N_host × 50 /1000
P_DC = P_CPU + P_GPU + P_MEM + P_host_other
P_PSU_loss = P_DC × (1/0.94−1)
P_network = N_rack × 100 /1000
P_IT = P_DC + P_PSU_loss + P_network
```

CPU/GPU使用率分母是安装容量，调度约束分母是可调度配额；二者分别记账。MEM只影响资源可行性，缺少带宽/访问数据时不驱动活动功率。CPU/GPU端点递增，全部设备基础功耗常驻；未从需求推断DVFS、kernel效率、动态关机或GPU碎片。

证据等级：**A**=公开核数/TDP/板卡参考规格，**B**=公开参考曲线，**C**=未校准研究假设。45/25W空闲、3W/DIMM、50W其他主机、100W交换机、恒定94% PSU和线性利用率关系均为C；205/250W只给设计参考端点，不是该任务的实测满载。相同GPU当量与实体功率对象一致，但理想可分割共享不证明真实MIG、MPS或独占放置可行。

## 5. 制冷、热状态与容量约束

### 5.1 架构与公共冷机

采用空冷冷机+冷冻水+送风系统+单节点，避免重新引入本研究不控制的冷却塔。HPE `dc-rl`和`sustain-cluster`提供EIR/PLR思想，但其将`CT_FAN_REF_P`传入冷机容量的接法不采用。V2冷机容量单位为kW_th，由安装设计IT确定，绝不由风机电功率代替。

使用[LBL Buildings v12.1.0原记录](https://raw.githubusercontent.com/lbl-srg/modelica-buildings/v12.1.0/Buildings/Fluid/Chillers/Data/ElectricEIR.mo)末尾 `ElectricEIRChiller_York_YCAL0033EE_101kW_3_1COP_AirCooled`：

| 参数 | 冻结值及解释 |
|---|---|
| 单模块参考冷量 /COP | 100.582kW_th /3.1；包COP，不含水泵 |
| 参考冷冻水 /空气 | 6.67 /35°C |
| 证据域 | 水4.44–10°C；空气23.89–51.67°C |
| PLR | 最小0.1；V2最大1.0；原记录1.15过载能力不使用 |
| 水流上限 | 4.3kg/s/模块 |
| 模块数 | `ceil(1.3×安装设计P_IT /100.582)`，不是按Train温度结果选容量 |
| 水温从属重置 | `T_water=6+0.5(T_supply−18)`，18–26°C送风对应6–10°C水温，全部在水温域内 |

定义六项温度函数 `f(a,x,y)=a0+a1x+a2x²+a3y+a4y²+a5xy`，x为出水温，y为曲线室外温度：

```text
CAPFT = f([-0.2660645697, 0.0998714035, -0.0023814154,
            0.0628316481, -0.0009644649, -0.0011249224], x, y)
EIRFT = f([ 0.1807017787, 0.0271530312, -0.0004553574,
            0.0188175079, 0.0002623276, -0.0012881189], x, y)
Q_available = N_module × 100.582 × CAPFT
PLR = Q_evaporator /Q_available
PLR_on = max(0.1,PLR)；cycle = min(1,PLR/0.1)
EIRFPLR = 0 + 1×PLR_on + 0×PLR_on²
P_package = Q_available /3.1 × EIRFT × EIRFPLR × cycle
```

零负载电输入为零。**公开PLR曲线恰好线性**，最小运行PLR加占空比后，平均电量随冷负荷线性；没有凭空加入部分负载节能、启动损失或模块启停优化。保留公开拟合原值：名义点CAPFT=1.049156、EIRFT=1.020807，所以一模块该点可用105.526kW、包COP约3.0368，而非强行归一成100.582和3.1。容量曲线在约29°C附近有小幅拟合隆起，不声称所有温度严格单调；高温35→50°C容量下降、EIR恶化，未为了曲线整齐重拟合。

按[EnergyPlus官方I/O说明](https://energyplus.readthedocs.io/en/stable/guides/input-output-reference/1.23-group-plant-equipment.html)，未单列冷凝风机比时空冷COP包含该风机。源记录该比值空白，故V2 **`P_compressor=0.9P_package`、`P_condenser_fan=0.1P_package`只作报告拆分**，两者之和等于原包电耗，绝不再叠加风机。10%不可从源数据识别，属于C，对总电耗和热平衡无影响，不能单独研究压缩机/冷凝风机控制。

### 5.2 严格界定曲线域

实际室外温度低于23.89°C时，性能函数取23.89°C边界并逐槽标记 `low_ambient_boundary=True`；实际天气仍进入建筑传热。这是**保守边界/最低冷凝压的研究近似**，并非实测低温曲线，也不是隐藏的免费冷却。YORK低环境控制资料仅支持该机制类别，不证明此数值等效性能。高于51.67°C时不外推，返回性能域无证据、零模型冷量、不可行状态。平台输入声明范围−5至55°C不等于这一范围均可安全运行。

三个Train片段的全部15,552槽均低于23.89°C。因此历史批次验证的是**边界假设下的交互与核算**，没有独立验证真实低温性能或高温曲线。固定20°C案例包COP约4.2331，不再长期硬封顶8；温度/水温方向与高温容量用另行预定的合成点检验。

### 5.3 热容、UA与空气/水侧

```text
C_eff = V_air ρ_air cp_air
      + (CPU-only质量 + GPU-host质量 +机架质量) × cp_equipment ×耦合比例
      + A_floor ×有效混凝土厚度×ρ_concrete×cp_concrete
UA = (四面墙面积+屋顶面积) × U /1000
C_eff dT/dt = P_IT + P_supply_fan + UA(T_out−T) − Q_coil
```

OM热容由空气195.566、设备/机架3080、有效楼板2177.280kJ/K组成，远小于V1的83500；该修正来自来源链与显式几何假设，不来自调度节碳成绩。按30秒子步积分，一次调度间隔900秒。

盘管额定=`1.3×安装设计IT`，设计空气温差10K；`K_air=Q_rated/10`，`Vdot_air=K_air/(ρ_air cp_air)`。风机500Pa、效率0.65，`P_fan=Δp Vdot/η/1000`。固定设计风量，无风机主动控制/真实风管压降标定。

冷冻水设计温差6K、cp=4.186kJ/(kg K)、密度1000kg/m³，泵100kPa、效率0.6。令`α=Δp/(ηρ cp ΔT_water×1000)`，则：

```text
Q_request = min(盘管额定, 最大水流×cp×6, max(0,K_air(T−T_supply)))
Q_coil = min(Q_request, Q_available/(1+α))
P_pump = α Q_coil；水流 = Q_coil/(cp×6)
Q_evaporator = Q_coil + P_pump
Q_unmet = Q_request − Q_coil
实际送风代表值 = T − Q_coil/K_air
Q_reject = Q_evaporator + P_package
P_HVAC = P_supply_fan + P_pump + P_compressor + P_condenser_fan
P_total = P_IT + P_HVAC
```

泵热进入水侧，水回流温度可由`T_water+Q_evaporator/(水流×cp)`推得；无流时不定义该比值。水侧约6K温升、含泵热时略高，空气侧由容量限制后的实际移热确定。设定送风通过理想阀门/旁通与从属水温重置实现，是聚合换热近似，不是详细盘管UA/阀门动态仿真。若冷量不足，实际送风达不到请求、热节点升温；不自动加冷量。

设施核算满足`(P_total+Q_envelope−Q_reject)Δt=C_effΔT`；冷机满足`Q_reject=Q_evaporator+P_compressor+P_condenser_fan`。电量kWh_e与冷量/热储量kWh_th分列，绝不相加。

### 5.4 安全过滤与控制权限

27°C为聚合代表入口控制限制，28°C为硬失败线；不是每架最高入口。安全器只用当前温度、当前IT及当前天气，预测下一槽保持这些输入时的响应，搜索18–26°C、0.5°C格点加原请求，按距请求由近到远选首个可行值。不假设“越冷越安全”的全局单调性。所有动作均不可行时，返回最低预测峰值动作但 `cooling_feasible=False`，保留实际升温；不能因此通过验收，越28°C更不能当安全运行。

同一接口支持：

1. 问题一：`authority='fixed'`，调度可改变，HVAC请求锁20°C；公共安全器仍可覆盖。
2. 问题二对照：`authority='independent'`，请求锁26°C，由同一安全器独立收紧。
3. 问题二联合：`authority='joint'`，任务排序/启动/推迟和18–26°C送风均可输入，末6h仍用共同尾段。

本次只运行前两类基线；没有把第三类接口当作已实现/已获胜的联合算法。后续要检验额外联合价值，必须公平比较第2与第3类；允许发现独立控制已足够好。

### 7.2 问题一：存在风险，但不能简化成“一推迟容量等待就一定增加”

18个同排序推迟配对中，DMR变差8个、队列峰增加16个、GPU启动峰增加4个，**容量等待总时长增加仅2个**。制冷副本是相同调度，不能当独立证据。推迟可减少某些容量等待总量，却消耗Slack并增加违约；这是应研究的风险机制，不能只看平均等待。

- OM瓶颈是GPU：EDF被阻挡606个任务槽、CPU/MEM为0；3个片段合计竞争105分钟。Threshold后GPU阻挡486、竞争90分钟，但主动等待85485任务分钟，DMR仍从1.352%增至1.429%。
- OH是GPU为主、CPU次之：EDF GPU3746、CPU1311、MEM0个阻挡任务槽，两类可重叠；竞争780分钟。Threshold竞争795分钟，容量等待任务1344→1429，主动等待77745任务分钟。
- OL没有容量阻挡、DMR为0；Threshold队列峰387来自**主动延后**，不能称容量拥塞。它提供低竞争机制对照。
- April的OM：123/3873→130/3873违约，即3.176%→3.357%；GPU启动峰增加19.603当量，队列123→387，但被动等待少1800任务分钟。OH同片段615→671违约，即15.879%→17.325%，必须如实保留过载。OH另外两段EDF为4.730%和1.882%，不能用汇总掩盖差异。

推迟配对总碳下降0.0506%–0.4809%，不是实际设施节碳率。CPU/GPU/IT完整能量在这些同任务配对中相同，碳变化来自时间权重及小的热/外界交换变化。算法开发应在这个既有风险结构下研究，不因成绩不佳重设容量或Deadline。[逐对结果](evidence/paired-deferral.csv)、[瓶颈](evidence/resource-bottlenecks.csv)。

### 7.3 问题二：耦合和安全机制有效；没有预设联合优势

所有Train案例温度≤26.999827°C、无冷量缺口、无不可行槽或性能域上界越界。独立可变控制每案例的安全覆盖次数最多264/288槽；固定20°C请求在OH的EDF、Threshold-EDF中各有5个覆盖槽（三片段合计），OM/OL为0。固定指请求规则固定，仍受共同安全器约束。负载增加确实改变IT热量、盘管移热及HVAC；设定温度通过热状态、水温/EIR及过滤作用产生电耗变化，温度约束不是天然满足。

18个相同任务调度制冷配对中，可变规则的总碳下降约0.4162%–0.5609%。**幅度较小而且只是本模型冷天气假设下的基线现象**，不说明联合控制一定优于独立安全控制。控制器更暖还会改变被动建筑散热；不能把全部差额归因于COP提高。没有额外联合控制实验；后续必须直接检验独立与联合的差异，若无增益则保留零结果。[逐对结果](evidence/paired-cooling.csv)。

### 7.4 共同背景、排空期与热储量

主增量=`工作负载总碳−同fragment/capacity的固定HVAC空闲总碳`，所有策略共用；另存 `matched_*` 以便解释控制本身改变空闲背景，不能替换主口径。上述固定基线共同背景约占总碳OM86.44%、OH79.28%、OL88.77%。**总碳始终与增量碳一起报告**，增量分母较小不意味着总量获得同幅改善。

以OM EDF固定控制为例，三片段到达期合计72h：IT4699.894、HVAC2202.046、总6901.940kWh、1088.783kg；排空期合计144h：IT5756.668、HVAC3518.736、总9275.404kWh、1630.199kg。到达期CPU/GPU/MEM均值配额利用率19.038%/32.441%/14.606%，排空期0.147%/0.584%/0.200%；到达峰CPU89.085%、GPU99.997%、MEM47.112%。这清楚显示长排空期常开背景占比，不能包装成连续负载节能。[全部分期24行](evidence/phase-summary.csv)。

## 8. V1/V2差异：不能说“模型修正带来真实节能”

只读取P1已保存的SLA1.5、相同EDF规则36行，**未运行V1**。36/36任务输入及调度哈希完全相同。V2总电量反而高8.524%–9.204%。设备数、CPU/GPU电量、主机基础和交换机电量不变；主要变化为：

1. 固定DIMM基础替代GB占用活动项，少量降低DIMM及PSU电量；减GiB不改变DIMM条数与3W基础，因此不能把两者混为真实内存节能。
2. 设计IT少了旧“DIMM满载5W”项，盘管/空气流量/风机按同规则随之改变。
3. EIR包COP在固定20°C冷天气约4.233，与旧长期封顶8不同，包电耗显著增加；风机分项边界也改变，应主要比较“压缩机+冷凝风机”整包。
4. UA、C和热轨迹同时改变，被动散热及净热储量不同。这些不能在未运行额外反事实实验时拆成各自独立因果贡献；这里只做严格的电分项算术和热守恒分解。

## 9. 八个问题的最终回答与适用边界

1. **为什么OM这样配？** 保留既有Train压力依据的10000/200/16000；双路32核扣4核/host需167台，200卡需50台四卡host，其余117台CPU-only。不是算法成绩倒推，也不是Alibaba真实硬件复原。
2. **需求怎样算功率？** CPU/GPU观测当量除安装容量驱动递增参考端点；MEM只限制容量、DIMM固定基础；PSU一次、网络一次。没有用usage伪装申请量或GB占用伪装访问活动。
3. **为什么该制冷架构？** 聚合空冷冷机+水环路+送风，足以表达本研究IT产热、受限移热和集中式控制，无需引入未研究的冷却塔。
4. **冷机参数从哪里来？** LBL版本化York空冷ElectricEIR完整公开记录，100.582kW/COP3.1、原温度函数和线性PLR；容量随工况改变，低PLR按最小运行及循环；明确低温边界假设与风机包边界，非实测标定。
5. **热容/UA怎样确定？** 参考几何、设备/空气/有限楼板热质量、外表面积×U；材料量级可查，参与质量、几何、U和换热控制仍为有界C假设，已给敏感性，不能宣称真实热点/热容得到验证。
6. **是否会能力不足？** 会。50°C高负载可出现缺口及越28°C；过滤无法凭空制造冷量。高温持续能力不足的轨迹标不可行、不得作为安全运行结论。Train本批无缺口，不等于所有工况都安全。
7. **两个问题能否公平研究？** 能，在上述理想共享池与单日批次范围内。问题一有已验证的GPU/CPU竞争、推迟和Deadline风险；问题二有能量闭合、工况容量、水温/设定温度、安全过滤与共同尾段。三种控制权限和总量/共同背景指标已具备，联合额外收益仍待算法研究检验。
8. **什么仍不能声称现实验证？** 真实申请量/用户Deadline、实例并发/设备放置、GPU共享可执行性、Gold/V100实际任务功率、DIMM访问功耗、PSU曲线、最热机架、湿度/凝露、真实低温机组性能、启动损失、详细换热器动态、参数校准、实际设施减碳率或联合算法优势。当前参考控制独立基线收益小，不能为制造优势修改参数。

据此，**没有需要阻止理想化算法开发的未解决结构性缺陷，停止平台重建并冻结V2**。物理不确定性必须在后续论文中披露并做预定稳健性验证；不能因算法效果不理想改研究对象。若未来扩大到真实连续多日、服务器放置或设施级部署，则属于新研究边界，需要独立数据与新版本，不能追溯改写本次结果。
