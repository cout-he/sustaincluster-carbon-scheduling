# V1 算法候选：先保护容量与 Deadline，再评估联合滚动优化

**推荐先选方案 A，验证“容量日历保护的碳感知 EDF”；随后用方案 B 检查联合预测控制是否还有额外价值。方案 C 作为统计资料充分后的备选。** 本文只完成文献筛选与适配设计，没有实现这些算法，没有训练、增加验收批次或开展正式对比。文中的时域、风险余量和求解预算均是待选方案，不是已经冻结的新实验参数。

P1 的直接证据决定方法重点，而不决定某个算法必须获胜：

- **资源竞争与个人 Slack 并不等价。** 在 4 月 4 日 OH、SLA=2、固定制冷的同排序 EDF 配对中，简单阈值推迟使总碳由 582.746 降至 579.753 kg，但 DMR 从 7.230% 增至 7.849%，容量等待由 48,405 增至 52,725 任务分钟，启动 GPU 峰值由 71.533 增至 120.820。当下仍有 Slack，不代表未来仍有资源。
- **不应把队列都当作拥堵。** OL 的阈值策略也有主动排队，但没有容量等待与违约。OM 的某些 FIFO 配对违约反而减少；“推迟总有害”不是结论。
- **联合控制有机制，但不能预设收益幅度。** V1 中 IT 功率产生热量，入口状态受移热、外界传热和历史状态影响。相同任务调度下，可变制冷改变 HVAC 用电且保持模型内安全；本批冷天气的 COP 全部位于上限 8，整体碳差仅约 0.262%–0.377%。不能用论文中的别处节能率预告本平台效果。
- **OH 不是默认可达≤5%的问题。** 某些片段立即 EDF 已明显高于 5%。方法必须报告过载和可行性，不能删任务、改变 Deadline 或把所有超过目标的结果归咎于算法。

## 3. 所有候选共同遵守的接口与信息边界

调用现有 `PlatformEnv.reset()`、`observation()`、`step(Action(...))`。动作包括所有待调度任务的排列、主动推迟集合、18–26°C 的送风请求；资源约束、账本、末 6 h 统一控制和热安全过滤仍由 V1 执行。算法不直接改环境内部任务或未来数组。

可用信息仅为已经到达的任务、已运行任务及其预计完成、当前资源与入口状态、当前/历史 CI 和天气。V1 假设任务的代理需求和 Duration 到达时可知；这是带执行时长信息的调度研究，不是未知时长估计研究。预测必须由这些信息或独立 Train 历史建立；真实未来 CI、天气和未到达任务只能属于另外标注的理想诊断，不能混入在线结果。

资源日历对每项任务预留 `ceil(Duration/15min)` 个完整时槽；Deadline 判定仍用真实 Duration，不能用向上取整的完成时间代替。运行任务按 V1 的下一个网格边界释放。三种资源必须同时可用；零 GPU 任务也要经过 CPU/MEM 检查。最晚启动是 `arrival + (SLA−1)×Duration`，合法网格起点不能越过它。

## 4. 方案 A：容量日历保护的碳感知 EDF（首选，低成本）

**目标：避免简单阈值把有个人 Slack 的任务集体推到未来无容量的时刻。** 这是一套拟实现的组合启发式，借鉴第 2 节 VCC 的容量前瞻和 CaWoSched 的开始时间搜索；不是上述论文算法的直接复现。

每 15 分钟执行以下流程：

1. 用运行任务的释放时刻建立 CPU/GPU/MEM 剩余容量日历，对已到达的待调度任务按 EDF 做“尽早可行插入”，获得一份参考开始计划。日历至少覆盖这些已知任务的最晚启动及完整执行，不在短预测时域末端遗忘长任务。
2. 对资源允许启动的任务，如果候选推迟一个时槽，重建受影响日历。只有在参考计划中原本可按时的已知任务仍可按时、该任务仍有合法起点时，才允许这种主动推迟。必要时按最早 Deadline/剩余 Slack 优先保护；小任务仍可回填，但不能破坏已经承诺的资源时段。
3. 只有满足上述容量条件，且预测的**完整运行时段**碳成本降低时，才选择推迟。最小版本先沿用因果历史阈值筛选候选，再以容量日历否决危险动作；有预测器后再比较完整运行碳积分。预测成本包括任务 IT 增量和同一 HVAC 模型的负荷响应，最终评价仍报告总碳。
4. 对未知未来到达，先不声称保证；可在独立 Train 数据支持下增加预先固定的容量余量。余量是自愿保守调度，不改变安装容量。不能看最终 DMR 再调余量。
5. 若参考插入已经不可行，记录“启发式未找到可行计划”，执行立即 EDF/回填并保留全部任务。不要把该失败当作数学不可行证明，也不要无限推迟来掩盖违约。

**为什么可能有效：** 现有阈值只检查本任务再等一步是否合法，A 还检查推迟对已知其他任务的影响。代价是可能放弃部分低碳机会；结果应呈现碳与服务的折衷。它不能保证未知到达下的 DMR≤5%，也不能保证优于立即 EDF。

**成本与最小后续验证：** 无神经网络；基础实现使用三资源槽数组和确定性列表调度。单次完整插入约为 `O(N×H)`，逐任务重建的保守实现最坏约 `O(N²×H)`，必须限制候选数并测运行时间，不能把复杂度写成恒定。先用小型合成任务验证“自己有 Slack、共同不可行”的反例、边界释放、回填与回退；获准后再比较立即 EDF、原阈值 EDF、A，并消融容量保护。第一步制冷规则保持相同，隔离调度作用。

## 5. 方案 B：有限候选的联合滚动预测控制（第二推荐，中等成本）

**目标：让任务开始计划和 HVAC 动作共同考虑未来热负荷，而不是调度完成后各自贪心。** 借鉴第 2 节 Wang 2025 的 MPC 协调思路及 Wang 2024 的安全修正原则；具体有限候选求解器是本平台拟适配设计，尚未验证。

在 A 的可行性保护上增加一个小型候选集：立即 EDF、A 的低碳开始计划、少量不同推迟程度的可行计划。对每个计划，枚举少量送风温度策略或分段常量序列，使用 V1 原有 IT/HVAC 动力学向前预测，然后只执行第一时槽，下一时槽重新规划。预测模型只在沙盒状态上评估，不改真实账本。

候选成本可写为：

`预测总碳 = Σ CI_hat[k] × (P_IT[k]+P_HVAC[k]) × 0.25 /1000`。

CI 单位 g/kWh，功率 kW，结果 kg；不能遗漏 HVAC 或固定背景。先筛除资源超限、已知任务风险恶化或预测温度不安全的方案，再在剩余方案中比较碳；过载时优先减少可识别的 Deadline 损失并明确记录，避免靠一个随意奖励权重让违约“划算”。完整责任窗口和任务数保持一致。

实现可以从 2–4 h、8–16 个时槽的热预测候选开始，但任务可行性日历仍覆盖已知任务的截止需求；这些只是待选范围。温度候选如 18/20/22/24/26°C，加上当前安全边界。不要枚举所有 `5^H` 序列；只用少量常量/分段模板或有固定预算的坐标改进。热状态与未完成队列必须加入末端约束或一致的延续代价，避免把热量/任务推到预测末端以外“免费”处理。

CI/天气先用持有值或仅在内部 Train 校准的简单预测，不必引入新网络；若未来单列完美预测诊断，必须与因果预测分开。所有实际动作仍经过同一个 V1 安全过滤器，记录请求、执行、修正次数；模型内安全不能表述为真实每架热点安全。

**为什么可能有效：** 同一个低 CI 时段可能同时成为高 IT 热负荷时段；滚动预测可在任务 Deadline 和温度余量内平衡运行时间与制冷时间。不过本次冷天气 COP 平台、固定风量和较大常开背景可能使 B 与简单规则几乎相同，这也是有效研究结果，不能通过改物理参数制造优势。

**成本与最小后续验证：** 需要状态复制、有限候选求解与预测误差测试，成本高于 A，低于从头建立混合整数非线性求解器。后续应比较相同任务计划的固定/安全可变/预测制冷，以及同样控制能力下顺序决策与联合决策；另报每步求解耗时、无可行候选率、热末端状态、预测误差。没有这些消融，不能把更多控制自由度误称为联合方法优势。

## 6. 方案 C：风险感知虚拟容量曲线 + 实时 Deadline 调度（备选）

**目标：用历史负载的不确定性给未来低碳时段留余量，再由实时任务层跟踪。** 借鉴 Radovanovic 的 VCC 与 Hall 2025 v3 的分布鲁棒分层规划；这是适配方向，不是现成保证。

上层根据独立 Train 历史和因果 CI 预测，生成时变 CPU/GPU 软使用预算，受真实容量上界约束，同时考虑 MEM 与 V1 边际 HVAC 成本；下层由 A 的资源日历/EDF 执行。紧急任务可以突破软预算，但绝不突破物理容量；所有突破及原因记录。没有未来到达时，不使用该片段真实未来工作量作为上层输入。

最小实现可先用经验分位数余量与线性规划；只有取得足够独立样本、明确分布支持集和误差验证后，才考虑 Wasserstein/DRO 风险约束。经验分位数版本不能叫“已获得分布鲁棒概率保证”。聚合容量风险也不自动等价于个体 DMR；必须把多资源持续占用、任务时长及 Deadline 映射重新论证。年度重复和平移片段不能充当独立样本来缩小置信区间。

**成本与最小后续验证：** 求解规模可控，但数据身份、样本独立性和风险校准工作量最高，当前只用三个验收片段不足以作保证。需要用户选定后，在允许的 Train 内建立按原始片段身份隔离的规划/校准/评估子集；检查 CPU 与 GPU 联合风险、未知到达下超预算、经验服务违约与保守性。收益不稳定时应保留 A，不以扩大复杂度掩盖问题。

## 7. 为什么暂不优先 PPO/MAPPO 或大规模约束求解？

| 路线 | 在本平台的判断 |
|---|---|
| 简单规则、EDF、Slack | 必须保留，可解释、便宜，是判断新增机制是否必要的基准；个人 Slack 要补资源日历 |
| 容量/队列预测 | 直接针对已观察到的未来聚集，先用确定性已知队列，再引入可验证的预测 |
| 约束优化、MPC | V1 状态和物理方程明确，适合 B 的有限候选版本；精确小例求解器可作后续验证工具，不是本轮新增实验 |
| 单 Agent RL | 将来可考虑替代有限候选排序，但必须先证明现有规则/MPC 的不足；仍需容量与热安全屏障 |
| 多 Agent /分层 RL | IT/HVAC 耦合存在，不等于需要两个神经网络；信用分配、训练稳定性与安全探索会增加成本，当前不推荐优先 |
| 资源弹性、跨站迁移、关机、MIG 放置 | V1 没有这些机制；本轮不能套用依赖这些能力的文献收益 |

目前没有新 RL 训练、网络结构、Reward 或超参数搜索计划。已有 V2/V3 Checkpoint 不用于 V1 性能背书。若后续选择学习方法，应先确定风险约束、因果观测和强基线，不能仅增加 Deadline/温度惩罚后称安全。

## 8. 选定方法后才执行的验证计划

以下为待批准的后续工作，本轮均未执行：

1. 冻结选定算法、因果预测器、规划时域、回退、计算预算和通过条件；设备/功率/任务配置固定于 V1，不按算法得分反向调整。
2. 先用合成小例验证资源日历、合法起点、策略等待与容量等待、不可行回退、热安全及预测末端，必要时与穷举小例核对。日历启发式失败与已证明不可行分开统计。
3. 在允许的 Train 内按原始身份隔离子集；同一原始日的年度平移/重复不能跨子集泄漏。原封存 Development/Validation/Test 继续不读；真正外部泛化需另行获准。
4. 用同源任务、相同容量、排序、SLA、72 h 责任窗口、设备背景和末端控制作配对。先 A 的保护消融，再 B 的相同控制权限消融；不得将 FIFO/EDF 差异算作碳推迟作用。
5. 同时报总碳、同口径增量碳、IT/HVAC 电能、DMR、完成率、JCT、两种等待、队列峰及持续时间、CPU/GPU/MEM 峰与瓶颈、启动聚集、温度/热余量、计算时间和回退率。报各片段最差服务结果，不能只报池化均值。
6. 单列因果与理想未来信息结果；后者只用于界定机会，不冒充在线可部署算法。小样本不提供虚假的统计显著性。若物理机制收益小，原样报告，不再寻找“好看的”功率曲线。
